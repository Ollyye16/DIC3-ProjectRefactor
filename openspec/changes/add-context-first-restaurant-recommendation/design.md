## Goals / Non-Goals

**Goals:**
- 讓交通可行性在最終選餐廳之前影響結果，而不是選完才附路線。
- 必要條件由程式判定，語言模型只負責理解輸入與撰寫說明。
- 每項推薦聲明都能回溯到原文片段或計算記錄。

**Non-Goals:**
- 不把向量檢索、知識圖譜或公車路線規劃宣稱為新演算法（DESIGN.md §1）。
- 初版不採自由遞迴的多代理架構；規劃器是可追蹤的工具工作流程（§5）。
- 不在本 change 撰寫研究評估計畫或研究限制章節（D013）。

## Decisions

| 決策 | 選擇 | 考慮過的替代方案與理由 | 來源 |
|---|---|---|---|
| 推薦順序 | 先召回情境候選，再分析交通 | 先找交通近的餐廳：會推薦不符情境的店；選完才附路線：交通無法回饋取捨 | D002 |
| 排名單位 | 餐廳；每店只保留最佳已驗證路線 | 以「餐廳＋路線」排名：路線多的餐廳會重複占位 | D008 |
| 條件判定 | 程式三值 T／F／U | 二值判定：把「資料不足」誤判為「不符合」或「符合」；加權扣分：高語意分數會抵銷違反必要條件 | D005、D007 |
| 語料來源 | 開發者挑選的 YouTube 影片，模組 1–3 離線 | 即時爬取或使用者自行新增：召回實驗無法重現 | D014 |
| 情境表示 | 固定版本化標籤表，抽取須附原文引文 | 自由文字標籤：無法查核與評估；不檢查引文：模型可能編造依據 | D015 |
| 逐字稿取得 | 人工 CC → 自動字幕 → Whisper，記錄取得方式 | 只用官方 API：無法下載非自有影片字幕 | D017 |
| Places 使用 | 只持久保存 Place ID | 保存 Places 評論建向量索引：違反平台政策 | §4、[Places API 政策] |
| 步行上限 | 依使用者指定的單段或總量定義查核 | 固定使用總量：與使用者原意不符 | D009 |
| 範圍 | 單次查詢；監控、重規劃、回程、照片、多輪記憶、重排模型延後 | 一次做完：先完成可驗證的第一版 | D003、D016 |

**提議中、尚未確認（不寫入 spec）：**
- D018：TDX 旅運規劃一律帶 `first_mile_mode=0`、`last_mile_mode=0`；若回傳任一路段 `type` 為 `drive`，該方案步行條件判 F。觸發原因是實測未帶參數時頭尾段回傳計程車，與官方文件不符。確認後應在 `bus-timeline` 新增一條 requirement。

## Risks / Trade-offs

- [需求解析錯誤會讓後續正確的程式驗證錯誤的條件] → 欄位保留與原句的對應；影響必要條件的歧義一律補問。
- [緩衝加大會減少錯過轉乘，但也排除原本可搭的方案] → 緩衝作為版本化參數，輸出揭露所採緩衝；不把三值狀態解讀為成功機率。
- [自動字幕或 Whisper 的店名錯字] → 以影片標題與說明交叉比對，無法確認者不歸屬。
- [TDX 官方文件與實際行為不一致（接駁預設為計程車）] → 見 D018 提議；確認前實作時須檢查回傳路段類型。
- [`NextBusTime` 與 `EstimateTime` 對不起來] → 兩欄位不混用；`NextBusTime` 語意待確認（O002）。
- [免費 TDX 方案每分鐘 5 次] → 候選數 `K` 須考慮呼叫頻率；`K` 尚未定案（O005）。
- [影片價格與營業資訊可能過時] → 只作參考並標示觀測時間；缺可靠來源時條件判 U（O012）。

## Open Questions

以下項目定案前不影響 spec 的行為規則，只影響參數或實作選擇。編號對應 DESIGN.md §16。

- O001：影片挑選標準（頻道、數量、年份、區域）。
- O002：`NextBusTime` 的語意。
- O003：哪些欄位必填、哪些可用揭露的預設值。
- O004：候車上限在介面上是否沿用式 4.1「準備完成起算」；若改為「抵站起算」，須先新增決策並修改 `bus-timeline` spec。
- O005：召回 `K`、門檻、片段聚合、混合權重。
- O006：正規化尺度、排序權重與證據品質成本。
- O007：不同資料的時效、衝突與缺漏處理細節。
- O008：上車／轉乘緩衝與用餐時長的預設方式。
- O009：技術棧、模型、資料庫、索引、圖譜與部署。
- O012：影片未提及價格或營業時間時的資料來源。
- O013：RQ1 是否以標籤自動生成查詢加人工標註小型資料集評估。
