# Proposal

> 來源：`DESIGN.md`（2026-11-10 版）。本 change 將 DESIGN.md 的預定設計轉為 OpenSpec 規格；專案仍在 Proposal 階段，尚未實作、尚未執行實驗。

## Why

在臺中搭公車用餐的使用者，需要同時符合約會、慶生或聚餐情境，又方便前往的餐廳。只做評論語意排名無法保證交通可行；選定餐廳後才附路線，交通條件也無法回饋到餐廳取捨（DESIGN.md §1）。因此需要一個先召回情境相符的候選、再以公車可行性與便利性決定最終排名的推薦流程。

## What Changes

- 新增需求解析與補問：將自然語言需求轉為 `q = (c, o, t_dep, B, L_max, W_max, N_max, D_meal)`，關鍵欄位不明時補問，不由模型猜定（§3.1）。
- 新增離線語料建置：由開發者挑選的臺中美食 YouTube 影片建立語料，以固定標籤表抽取情境並檢查原文引文（D014、D015、D017）。
- 新增情境召回：以 BM25、向量或混合檢索召回片段，依餐廳去重形成候選（§9）。
- 新增公車交通分析：透過 TDX 取得公車方案並建立上車、轉乘、抵達與離店的完整時間線（§7）。
- 新增必要條件三值查核：預算、營業、步行、上車、轉乘逐項判定 T／F／U 並依固定規則聚合（§8）。
- 新增餐廳排序：只對全 T 方案評分，每店保留最佳已驗證方案，最多輸出三間不同餐廳（§9、D008）。
- 新增推薦輸出與例外處理：推薦說明只能使用已保存的事實；未知項與已驗證推薦分開呈現；不靜默放寬條件（§3.2、§10、D007）。
- 新增證據來源與時間紀錄：每項判定與推薦聲明可回溯至來源片段或計算記錄（§11）。

## Capabilities

### New Capabilities

- `query-understanding`：將自然語言需求轉為固定欄位、補問缺漏欄位、拒絕無效單位。
- `corpus-ingestion`：從開發者挑選的影片建立語料，抽取情境標籤與原文引文，完成餐廳實體對應。
- `context-retrieval`：依用餐情境召回有評論片段支持的候選餐廳，並依餐廳去重。
- `bus-timeline`：取得候選餐廳的公車方案，建立帶日期的出發、上車、轉乘、抵達與離店時間線。
- `constraint-checking`：對餐廳與路線組合逐項判定必要條件為 T／F／U，並聚合為組合狀態。
- `restaurant-ranking`：對已驗證方案評分，每店保留最佳方案，輸出最多三間不同餐廳。
- `recommendation-output`：呈現推薦、暫定項與無結果原因，並確保說明不超出已保存證據。
- `evidence-provenance`：保存來源、時間欄位與判定紀錄，使每項聲明可回溯。

### Modified Capabilities

（無；本專案尚無既有 spec。）

## Impact

- 文件：本 change 的 specs 取代 DESIGN.md §14 所述「尚未建立獨立的 `specs/spec.md`」；DESIGN.md 仍保留決策紀錄（§15）、待確認事項（§16）與變更紀錄（§17）。
- 外部資料：YouTube Data API、Google Places API、TDX 旅運規劃與公車 API（§4）。
- 範圍外：行程中監控、延誤重規劃、回程、使用者自行新增來源、照片判讀、多輪對話記憶、重排模型、停車推薦、多使用者協調（§2、D003、D016）。
- 未定案：技術棧、模型、資料庫、向量庫與部署（O009）；召回 `K`、門檻與排序權重（O005、O006）。這些不寫入 spec，列於 design.md 的 Open Questions。
